# Technical Writing

**Technical Writing analysis** is a diagnostic lens, not a template generator. Use it when you want to ask how a technical passage serves a reader: “Does this quick start show how to know the command worked?” or “Is this realistic example hiding the one concept I am teaching?” For a selected word or short phrase, expand **Technical writing analysis** in the Inspector and write your question; you do not need a technical [Writing Brief](writing-brief.md) or section role for this. **Run Technical Writing analysis · whole piece** appears when the brief has a technical content type or the selected section has a technical role.

It can consider tutorials, quick starts, how-to guides, explanation, reference, troubleshooting, architecture documents and talks. Conventions are **lenses** for asking what the reader needs, not mandatory outlines. A tutorial might deliberately begin with a failed attempt; a quick start may need a concept before its first command; a talk can use a reveal or callback. The tool should explain what that choice gains and costs rather than call it wrong by default.

It distinguishes an **action** (“run the command”), an **expected result** (“a server starts”), **verification** (“a response confirms this instance is working”) and **recovery** (“what to check if the response is missing”). These may sit in one paragraph; you do not need four headings. It can ask about prerequisites, branch points and the difference between an illustrative example and production guidance. The smallest useful question matters more than reciting a checklist.

Add [Sources](sources.md) when factual claims need grounding. The tool can compare relevant supplied excerpts with what the passage says and point out missing support or a clear contradiction. It does **not** execute commands, test your software, browse for independent facts during this writing analysis or prove an external claim true. Without supporting material, it should discuss the reader's likely interpretation rather than certify a technical fact.

The result is **analysis and questions only**, not a replacement draft. Your own voice, including fragments, humor or an intentional inversion, remains yours. [Workbench](workbench.md) explains how ordinary proposals differ; [Models and routing](models-and-routing.md) explains Offline limits.
